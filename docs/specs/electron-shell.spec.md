# Electron host specification

## Process boundaries (HOST-01)

The desktop host reuses the web client, Hono host and API. Production opens no TCP listener for pages or API. Main owns windows, the dedicated session, protocol mapping, utility lifecycle and restricted system bridges. Windows and service workers share one sandboxed CommonJS preload. Before ready, register the application scheme with standard, secure, supportFetchAPI, stream, corsEnabled, codeCache and allowServiceWorkers privileges. The utility process runs `createWebApp`, SSR or SPA hosting, static files, API and port-fetch as ESM under Node resolution conditions. The renderer uses the same web client build without Node integration.

Build outputs are `main.cjs`, `preload.cjs` and `utility.mjs`. Main must not import `@repo/server` or top-level await `app.whenReady()`. Shared contracts are browser-safe. Transport packages remain independent of Electron and testable under Node. Electron is pinned in package metadata; upgrades require validation rather than a runtime version allowlist.

## Protocol mapping (HOST-02)

Requests follow `app://app` → dedicated-session protocol handler → internal HTTP URL → MessagePort/port-fetch → utility `createWebApp().fetch(Request)` → streamed response. Reject targets outside `app://app`. `main/app-url.ts` defines the stable scheme/host/origin and shared URL check; keep that origin independent of product names and APP_ID. Changing it requires a browser-storage migration.

The internal origin provides server URL/same-origin semantics, not a listening port. Map URL, relevant Origin/Referer and response Location. Non-GET/HEAD requests receive a trusted internal Origin and Sec-Fetch-Site for Hono CSRF and Router checks. Strip renderer-supplied Cookie and X-Desktop-* before injecting actual host state and preferences. Web hosts remove desktop headers; headers cannot establish desktop identity.

Server redirects use relative paths, including Router `.data` redirects embedded in response bodies. Do not derive public absolute links from internal request URLs. Static files and SPA HTML belong only to the web host. The development proxy uses manual redirects to preserve status and Location.

## Transport and utility lifecycle (HOST-03)

Port-fetch multiplexes request IDs with Request/Response headers, status and bidirectional bodies. Return response streams as soon as headers arrive. Acknowledgement windows bound unconsumed bytes and pause upstream reads. Chunks use standalone Uint8Array buffers so cloning a subarray does not copy a larger backing store. No zero-copy guarantee applies; Electron ports receive no ArrayBuffer transfer list.

Cancellation, timeout, port closure, early response and stream error clean up both ends idempotently. Closed ports reject new requests. Before response handoff, main correlates the application session's webRequest disconnect with its protocol request by network ID, including during cookie lookup. The protocol handler owns the application session’s `onBeforeSendHeaders`, `onErrorOccurred` and `onCompleted` listeners. Registering another listener for the same event replaces the existing one. Main removes the internal correlation header before forwarding. After handoff, cancelling the response body also cancels the upstream request. Utility handlers propagate their request signal to downstream work. Both desktop modes bound the upstream header wait to 60 seconds while SSE and download bodies may continue. The development proxy retries only GET and HEAD on transient connection failures.

Adapt MessagePortMain event shapes and start semantics, transferring ports only after utility spawn. Utility state is explicitly idle/starting/running/stopping/stopped. Concurrent starts share readiness. Fork-to-ready times out after 20 seconds; shutdown has a 3-second grace period. Shutdown forbids automatic restart. A utility retired or stopped before it spawned is killed as soon as it exists. Increasing generations coordinate restart/readiness with window recovery.

## Identity, trust and CSP (HOST-04)

Host identity comes from `createWebApp({ shell })`; development uses WEB_SHELL configuration. Stable shell facts and trusted per-request window/preferences data are distinct. SSR supplies root seeds; SPA reconnects through preload according to the layout lifecycle.

The renderer uses contextIsolation, sandbox and no nodeIntegration. Enable nodeIntegrationInSubFrames to run the sandboxed preload in child frames. Keep webviewTag disabled. Only the main frame receives the desktop capability bridge, teardown and first-paint signal. Subframes receive only the cookie shim and fetch wrapper where HOST-09 permits them. The application has a dedicated persistent session. Navigation and redirects stay on app://app. Main-frame external http/https/mailto links go to the system browser; external sub-frame navigation and redirects are blocked without opening another application. Same-origin sub-frame navigation remains allowed. New-window requests for app://app open independent application windows with the same session, preload and shared utility. Each window owns its chrome IPC and recovery state. Dock activation and second-instance launches can reopen the primary window while independent windows retain their state. Same-origin windows that retain an opener can share a Chromium renderer and recover together after its exit. A healthy document survives replacement of the shared utility. Both window creation paths retry the pending visual mirror, then use its current effective color scheme. A child can have a fixed appearance selected at creation. Its preload receives that appearance from main in the synchronous visual sample for its registered webContents, including when it retains its opener. Capability IPC verifies the registered BrowserWindow, its current webContents, current main frame and frame protocol/host. Frame cookie channels also serve eligible subframes and validate senderFrame.origin and registered webContents ownership in the application session.

The desktop demo assigns the settings route a window key. Reopening settings from any window restores and focuses its existing window without reloading the document. Closing that window or navigating it away releases the key. Other new-window requests keep their normal popup and opener semantics. Automatically placed siblings cascade within the opener's display work area where the window manager permits positioning. Explicit popup coordinates and dimensions take precedence.

Capture main exceptions in logs instead of blocking default dialogs. Once stdout fails, the main logger drops later lines instead of reporting the failure to the same stream. Protocol/port failures are explicit. Logs omit credentials, full bootstrap/preferences and sensitive queries. `main/log-url.ts` bounds URL fields and removes credentials, query and fragment; opaque URLs expose only their scheme. Error messages/stacks and forwarded main-frame console text redact recognized absolute URLs while retaining diagnostics. Paths, free text and other structured fields still require caller-level care; the main logger does not sanitize forwarded utility output. Single-instance locking, utility shutdown and listener cleanup are required. A window whose renderer exits while the window is closing is destroyed rather than reloaded, so quitting cannot stall on it; a page that vetoes unload keeps its window and recovery. Windows log `window unresponsive` (warn) and `window responsive again` (info). macOS activation can create/register a new window after closure. Desktop identity is not business authorization and never grants arbitrary proxy destinations.

The web host owns CSP. SSR uses one document nonce across React, ServerRouter, Links, ScrollRestoration and Scripts; revalidation cannot replace the active document nonce. Static SPA/prerendered HTML uses hashes, identical for GET/HEAD, and does not serve document ranges. Production script-src excludes unsafe-inline. Inline chrome safety styles require the configured style policy independently of script policy.

## Development and startup (HOST-05)

`pnpm dev:desktop` starts a separate desktop-mode Router dev server and Electron. Pages remain app://; main proxies to development HTTP without running utility. Mapping/trust rules remain the same. Development watches builds, restarts Electron after main/utility changes, reloads after preload changes and waits for the old process to exit. The default port is 5174, configurable with DESKTOP_DEV_PORT; HMR host/clientPort are explicit. Development runs the dev build profile (HOST-11) on `<userData>-dev`; DESKTOP_USER_DATA_SUFFIX, read only by the dev build, changes the suffix. Electron is started without `windowsHide`, which on Windows hides its first window (measured on Windows 11); console children keep it.

At ready, the utility starts in parallel with the cookie store read. Main creates the first hidden window after that wait (HOST-09). In SSR builds it first copies a valid native visual record into a differing session visual cookie through the same script jar and serializer as the page. A missing record leaves the cookie untouched. A read or write failure is logged and startup continues with the preload mirror. Document requests await utility readiness. A trusted preload notification after two animation frames shows the window; ready-to-show has a one-second fallback. Bootstrap enhancement does not gate display. Every launch that starts the application logs `{"buildProfile":…,"msg":"build profile"}` at info as its first main-process line; a release launch refused for remote debugging logs only the refusal, and the Windows cookie key writer copy (HOST-09) logs nothing. It then logs `main window loaded and shown` at info once per process, when the primary window holds a finished document answered with a 2xx status and is shown; HTTP error documents, Chromium error pages and hidden windows never produce it. A window counts as shown on its `show` event or, right after the application itself showed it, when it reports itself visible: on macOS `show` follows occlusion and does not arrive while the screen is locked (measured). That second path has unit tests only; it has not been exercised in a real locked session. LOG_LEVEL cannot suppress either line; external launchers depend on both. Utility NODE_COMPILE_CACHE resides in userData. Startup evaluation compares repeated same-environment medians and stage timings, not a universal cold-start promise.

## Build and packaging (HOST-06)

Build web first, then the three desktop entries of one build profile (HOST-11), then electron-builder with that profile's leaf configuration (`electron-builder.test.yml` or `electron-builder.release.yml`, both extending `electron-builder.base.yml`). Root package:desktop:test/package:desktop/dist:desktop include builds; package-local packaging scripts consume existing builds. Packaging and every unpackaged test launch (`checkLaunchInputs()` in `scripts/launch.ts`; dev launches are not checked) first check that the profile's utility bundle and `apps/web/build/client` come from the same web build: the utility embeds the SHA-256 digest of the entire client tree recorded at Web build completion (relative paths and file contents). Packaging and launch recompute it from the current files, check that every hashed client asset the utility references exists, and require the server entry to match the SHA-256 recorded in `.vite/<profile>/web-server.json` when the utility was built. ASAR contains the profile's entry bundles and package metadata, without source maps, module records or the web server record. Client resources are copied to resources/client and served by utility. Bundled web/server dependencies are not duplicated as runtime node_modules. Only required external native modules belong in dependencies; native modules require Electron ABI and rebuild-policy verification.

Root `build`, `build:desktop`, `build:desktop:test`, `package:desktop`, `package:desktop:test` and `dist:desktop` run their child builds with NODE_ENV=production and without inherited development server variables. Test and release bundles are minified, replace process.env.NODE_ENV with production and never embed a development server URL; only the dev profile, built in watch mode by `dev:desktop`, does. The utility always hosts a built application and receives NODE_ENV=production, regardless of its parent's environment. Building only the desktop entries (`pnpm --dir apps/desktop build` or `build:test`) consumes the existing web build, so use `build:desktop` or `build:desktop:test` before packaging.

`apps/desktop/package.json` supplies `productName`, checked against `electron-builder.base.yml`. It determines the default Electron app name and hence userData; builder `appId` is separate. Choose these values together with shared `APP_ID` for each derived project. The generic preference store uses prefs.json, the stamped visual mirror uses visual.json, and the utility uses compile-cache/ within userData.

Packaged E2E derives macOS bundle/executable and Windows executable names from productName. Linux follows electron-builder's default lowercased package name, not productName. Packaged test launches default to `out/test`. Both `start:desktop` and `verify:release` locate the release application in `out/release`; the verifier also uses the test package as a positive control. These lookups support the existing platform/architecture output directories and assume the default executable name. Name validation accepts a leading ASCII letter and subsequent ASCII letters, digits, spaces, dots, underscores or hyphens, rejects trailing dots/spaces and Windows reserved filenames, and keeps builder sanitization from changing the expected path.

Both packages take their fuses from one table (`FUSES` in `scripts/fuses.ts`), flipped by each leaf configuration's afterPack hook: RunAsNode, NodeOptionsEnvironmentVariable and NodeCliInspectArguments off; CookieEncryption, EmbeddedAsarIntegrityValidation and OnlyLoadAppFromAsar on. The test package differs only in keeping NodeCliInspectArguments on, which Playwright's Electron driver needs. Every packaged test launch first reads the six fuses back from the final binary (`checkLaunchInputs()`) and refuses a package that does not match the test column; `verify:release` reports the release read-back as its check 1 and runs its other checks regardless. Unpackaged runs use the checkout's Electron, whose fuses are never flipped, so they have no cookie encryption and no asar checks.

Installers (macOS dmg/zip, Windows NSIS as an assisted installer that lets the user choose the installation directory and a per-user or all-users installation, Linux deb/rpm; rpm requires rpmbuild) are built only from the release profile (`dist:desktop`, into `out/release`); `out/test` holds only the unpacked test app. Build the Windows installer on Windows. With electron-builder 26, different installer and uninstaller icons caused a macOS cross-built uninstaller to stop with "Installer integrity check has failed" ([electron-userland/electron-builder#10258](https://github.com/electron-userland/electron-builder/issues/10258), fixed in 27). The template now uses the same application icon for both. Uninstalling a macOS cross-build with this icon has not been verified on Windows. An unpacked Windows app cross-built on macOS starts normally (measured on Windows 11 arm64). On Windows, `verify:release --distribution` requires valid Authenticode signatures on both the unpacked application and the native NSIS installer. The installer accepts an empty directory or a registered installation with a file-scoped uninstaller; upgrades and uninstall remove only packaged files and empty directories. A missing registered directory on an accessible local fixed drive is treated as a first install. The app-builder-lib patch keeps installer initialization in the NSIS plugin directory so a silent `/D` selection cannot recreate a missing directory before inspection. The destination check runs after electron-builder selects the final install scope and performs any required elevation. After validating the new destination and all applicable scopes, the installer removes the stale registration without invoking its uninstaller. An empty registered path, an unavailable drive, an access error, or an existing directory without a file-scoped uninstaller blocks installation. No signing identity is configured. Signing, notarization, distribution channels and automatic updates are not supplied as completed release services. Linux installation must satisfy sandbox permissions; --no-sandbox is not a default release solution.

## Bidirectional channels (HOST-07)

`@repo/channel` provides MessagePort/WebSocket adapters and relay with ordered delivery, backpressure and bounded connection/queue handling. Message ports have no native byte backpressure, WebSocket local drain does not prove remote application progress, and empty messages still require frame limits; acknowledgement and drain are not business persistence. Producers await whenDrained; send itself does not block or drop frames. Channel is distinct from request/response port-fetch. The template does not expose an application gateway connection, renderer sandbox connection or BFF streaming route merely because the transport package exists.

## Preferences (HOST-08)

Page scripts under app://app can read and write non-HttpOnly cookies. Display preferences needed for the first SSR render still use the preference API and desktop prefs.json. Web names cookies by concatenating `PREFERENCE_COOKIE_PREFIX` and the key. The prefix is `cookieName("pref_")` from `@repo/shared` (default `framework-app_pref_`). Cookies contain JSON values, percent-encoding characters disallowed in cookie values, Path=/, SameSite=Lax, one-year Max-Age and Secure on HTTPS. Duplicate names use the first, most specific path match. Desktop uses main-process memory and userData/prefs.json, atomically replaced after temporary-file fsync; transient Windows rename failures retry within about 100ms. Values take effect only after successful persistence.

The web helper is `~/platform/electron/preferences`, with host contexts in `~/platform/electron/shell`. Old `pref-*` cookie names are not read; resetting those template preferences is intentional and no compatibility layer is added. Visual preference localStorage and visual cookie names keep their existing derived values.

Desktop injects x-desktop-prefs on every request. Preload setPref/removePref invokes validated main IPC. Loader/action `getPreference(context, key)` returns undefined for absent/invalid values. Host context chooses the source: web cookies or desktop request preferences, never an untrusted request-selected mode. `useSetPreference()` writes and revalidates; null deletes; failures reject with PreferenceError/reason. `writePreference(shell, key, value)` works outside React without automatic revalidation. After a changed value is persisted, other open desktop documents coalesce notifications and revalidate their active loaders, including a final refresh for changes made during an in-flight refresh. A new subscription checks its rendered snapshot against the main store to cover writes during hydration. Business code uses these helpers rather than shell branches or direct cookie writes.

Bridge writes and removals persist across relaunches in both builds. Request-time preference rendering and root loader revalidation apply to SSR builds. There is no general client-side read API for SPA/clientLoader. Supply loader data or design an explicit read bridge when needed. Keys start with a letter and contain letters/digits/underscore/dot/hyphen, at most 64 characters. Values are strings of at most 1024 UTF-16 units, finite numbers or booleans. Both hosts enforce both 4096-byte aggregate limits: ASCII JSON with non-ASCII escaped, and the encoded preference cookie header using that same prefix including separators. Oversized updates reject before writing; deletion is always accepted.

Preferences are user-controlled display settings, never credentials, sessions, authorization inputs or bulk data. High-frequency changes persist on commit rather than every frame. Main is the final validator. Invalid requests return rejected without changes; disk failure returns persist-failed with the previous value intact. Malformed files become empty and invalid entries are discarded. Logs omit preference values. Browser desktop-header spoofing is stripped before trusted injection.

## Server cookies (HOST-09)

Main uses `@repo/electron-cookies` for both utility and development proxy requests. Chromium does not handle cookies for app:// or process Set-Cookie on protocol-handler responses. The dedicated session stores host-only and domain cookies at the private HTTPS origin `https://app.desktop` in both modes. Both packages enable the CookieEncryption fuse. With Electron 45’s default Linux configuration, a usable Secret Service or KWallet supplies a secret for the `v11` key. Without one, or with `--password-store=basic`, Chromium uses the fixed built-in `v10` key, which only obfuscates values on disk. Linux test launches select the basic store and cover only that path. Unpackaged runs store cookie values unencrypted. [Chromium basic key](https://github.com/chromium/chromium/blob/156.0.8078.48/components/os_crypt/async/browser/posix_key_provider.cc#L16-L33) · [Chromium Linux keyring selection](https://github.com/chromium/chromium/blob/156.0.8078.48/components/os_crypt/async/browser/freedesktop_secret_key_provider.cc#L207-L220)

Replace renderer Cookie headers with eligible stored cookies matching the request path, longest Path first. Process the first 50 Set-Cookie fields in header order. Wait for accepted mutations and flushStore before delivering the response, including replacement of persistent cookies by session cookies. Strip Set-Cookie before renderer delivery. A store call in flight when the network service dies can hang (measured on Electron 45, macOS). A rejected lookup or one that times out after five seconds returns 503 with Retry-After before forwarding, or a transport error for main-document recovery. Cancellation ends the lookup. Response writes and flush share a separate five-second deadline and continue after request cancellation. A timeout leaves cookie state unknown and logs a warning.

On navigation and subresource responses from the secure application scheme, apply the same request-source policy to Clear-Site-Data as to Set-Cookie. An ASCII comma-separated list containing `"cookies"` or `"*"` clears host-only and domain cookies for the private storage host across all paths, including HttpOnly and cookies set with Partitioned. Flush before delivering the response. Chromium independently checks the HTTP list for these exact quoted tokens and suppresses Set-Cookie on the same response. Unrecognized tokens have no effect. [Chromium clearing rules](https://github.com/chromium/chromium/blob/156.0.8078.48/content/browser/browsing_data/clear_site_data_handler.cc#L203-L234) · [Chromium Set-Cookie processing](https://github.com/chromium/chromium/blob/156.0.8078.48/net/url_request/url_request_http_job.cc#L997-L1003)

After all windows accept quit, flush with a two-second bound in parallel with utility shutdown. Wake-index finalization runs alongside with its own two-second deadline (quitTimeoutMs); on timeout main warns once and starts no further index writes, and the file stays the last complete atomic write. A window that cancels quit retains its working host and recovery. Session cookies survive reload/window reopening but not process restart. Persistent cookies survive restart, and a crash or kill after the response that set them. On Linux a signal to the application's whole process group (a session logout, or a direct launch interrupted from its terminal) can make Chromium abort instead of quitting (measured: the GPU process dies first); nothing already flushed is lost. `pnpm --dir apps/desktop start:test` keeps the application in its own process group and passes signals to the main process only.

On Windows the encryption key's only copy on disk is in `<userData>/Local State`, which Chromium writes about 10 seconds after a new profile starts or at a clean quit (measured on Electron 45, Windows 11 arm64; [electron/electron#55978](https://github.com/electron/electron/issues/55978), open). A test or release launch whose Local State has no key therefore, once it holds the single-instance lock, runs a copy of the app with `--desktop-cookie-key-writer` on the same userData and waits for it (at most 5 seconds): the copy lets Chromium create the key, prints a probe encrypted with the synchronous safeStorage API and quits at ready, which makes Chromium write Local State and its own directories (such as Crashpad and caches); the copy writes nothing of the application's. The launch reads Local State only after its main script's synchronous part, so it starts on that key (measured, not documented by Electron); it logs `cookie key stored before start`, then, once its first window is on its way, whether it decrypts the probe (`cookie key checked: this launch uses the stored key`, or an error). The probe relies on safeStorage sharing the cookie encryption key, measured for the synchronous API only; Electron 45 marks that API deprecated, and if it disappears the launch logs that it cannot check the key, which stays stored. The writer's wall time is noted in the boot profile as `cookie-key-writer-ms` (measured 100–300 ms on a profile's first launch on Windows 11 arm64, with later launches only reading Local State; Windows x64 untested); every launcher run on Windows includes it, as each uses a fresh profile. The writer is a temporary workaround to be removed once Electron persists the key when it creates it.

Only a Local State that is absent or parses without a key counts as missing. After a run that leaves the key missing, `cookie-key-writer-failed.json` in userData records the time and application version; for a day, launches of that version skip the writer with a warning, and a launch that finds the key deletes the record. An unreadable or unparseable Local State is retried briefly. If the initial check remains inconclusive, the launch logs a warning and skips the writer. Inconclusive reads leave no failure record; the next launch checks the file again. A packaged profile without a stored key can lose persistent cookies set in a first launch that dies within about 10 seconds; unpackaged launches do not encrypt cookies and lose nothing. An uncaught error in the writer ends it with a non-zero status instead of Electron's blocking dialog. Dev builds never run the writer. The writer is refused like any release launch with a remote debugging switch and receives only `--user-data-dir`, `--disable-gpu`, its own switch and, unpackaged, the application directory. Windows 11 arm64 tests cover native arm64 and emulated x64 packages. Both cookie hard-kill cases pass with the x64 executable. A Windows filesystem and process test covers spawn failure, malformed Local State, retry suppression, expiry, version changes and recovery with the real key writer. The writer crash exit has unit coverage.

Cookies attach only to app:// handler upstream requests, never arbitrary targets. Code must not request the storage origin in the application session. The .desktop suffix is not a reserved TLD; future delegation would create a risk if such network requests were allowed. The renderer remains restricted to app://app. The production CSP does not allow that storage origin; the development CSP allows ws: and wss: to any host for Vite HMR, so in development only the rule above keeps code from opening a WebSocket to it. Logs omit Cookie and Set-Cookie values; store rejection and replacement diagnostics may include the cookie name.

E2E routes mount only with DESKTOP_E2E=1 in dev and test builds; release builds contain neither the routes nor the variable name (HOST-11). Development defaults to `<userData>-dev`. Test launches use isolated profiles by default. With `start:test --user-data-dir=<dir>`, the launcher uses the supplied directory and keeps it on exit; later launches using that directory share its persistent cookies.

### Script cookies

Server Set-Cookie and the synchronous document.cookie setter share a text parser. document.cookie writes carrying HttpOnly or targeting an existing HttpOnly cookie are ignored. Cookie Store set() and delete() targeting an existing HttpOnly cookie reject with TypeError, as in Chromium. The asynchronous Cookie Store API validates structured fields and rejects invalid writes with TypeError. Its default cookie is host-only, Secure, SameSite=Strict, Path=/ and session-lived. All three entry points write to the same Chromium store. Script reads and change notifications expose only non-HttpOnly cookies.

Preload captures the document creation URL in the isolated world before page code runs. Main requires a live senderFrame with the application origin, an owned webContents in the application session and a valid application cookie URL. Use Electron's senderFrame.origin for the effective origin and compare scheme and host for URL validation. History changes do not alter the cookie URL. document.cookie accessors and CookieStore methods borrowed from another same-origin window use the receiving document's or store's creation URL; detached documents and receivers from unshimmed windows keep native behavior. Cookie Store resolves explicit relative read URLs against that creation URL, strips the input fragment and compares the result to the original creation URL. Same-origin srcdoc inherits its parent's recorded creation URL. Without that record, srcdoc keeps native cookie access and still receives the fetch wrapper. Same-origin blob: documents also keep native cookie APIs and receive the fetch wrapper. Opaque frames use Chromium's native access checks.

The protocol handler cannot observe the original fetch credentials mode. Window and service worker preloads mark application-origin fetch requests with `x-desktop-omit-cookies` when the effective Request uses omit. They remove a stale marker when credentials change, including when a service worker reissues a request with include. Other destinations receive no added marker. Main reads the original headers for cookie policy and strips the marker before forwarding.

| Electron request.initiatorOrigin  | Source                                                                                                       | Send Cookie and accept Set-Cookie      |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------ | -------------------------------------- |
| Absent                            | Browser-initiated request such as main-process loadURL                                                       | Yes, unless the omit marker is present |
| APP_ORIGIN                        | Application frames, srcdoc, dedicated workers, shared workers, service workers and page-initiated navigation | Yes, unless the omit marker is present |
| Any other value, including "null" | Opaque frames, other custom schemes and foreign origins                                                      | Never                                  |

The jar enforces both directions independently of navigation and CSP restrictions. Routes returning sensitive data without cookies must account for opaque-origin callers. Direct HTTP(S) traffic uses Chromium's native cookie handling. Multiple cookie-bearing custom-scheme sites and intercepting HTTP(S) with protocol.handle are unsupported.

Changes in the session store reach listening windows as CookieChangeEvent instances, filtered by document identity and cookie path. Inserts, value changes and expiry-only updates populate changed. Deletions omit value and expires. Identical rewrites and intermediate overwrite removals produce no event. Replacing a visible cookie with an HttpOnly cookie produces no script-visible change event in either a window or a worker.

Main binds worker IPC to a live worker version with an application scope in the dedicated session. Cookie reads use that worker's script URL. Native registration.cookies owns subscriptions and defaults their URL to the registration scope. Main loads a persistent wake index before listening for changes. Serialize subscribe, unsubscribe and unregister per scope. Persist the wake hint before native subscribe and remove it after successful unsubscribe unless a timed-out subscribe pinned it. Successful wrapped unregister clears the scope and cancels queued deliveries and retries. Match name and cookie path to the subscription URL before waking, recheck eligibility against the event time before sending, and check the active worker and its native subscriptions before dispatch. Electron 45 reports missing registrations and transient startWorkerForScope failures alike. Each scope queues up to 128 waiting changes; overflow drops the oldest and warns once per backlog. Queued changes share one immediate wake and retries after 100, 400 and 1,600 ms. Each attempt waits up to 60 seconds (wakeTimeoutMs) for startWorkerForScope() to settle; a timeout counts as a failed attempt, and a later result from that attempt is ignored. If the worker is destroyed or sending fails before it reports started, retry the change as the oldest waiting event on the same schedule (subject to the 128 limit); after started, destruction releases the task without redelivery, and a dispatch timeout before started warns and drops the event. If the last retry fails, warn once, drop the queue and retain the index; the next matching change starts a fresh wake. Three consecutive exhausted schedules for one scope in a launch make its hints dormant: persisted, never woken, until a wrapped subscribe() succeeds for that scope; a successful wake resets the count. Each wrapped subscribe() accepts up to 128 entries and names up to 4,096 UTF-8 bytes; the index holds up to 256 subscriptions per scope and 128 scopes, counting capacity reserved by pending subscribes. Unsubscribe and unregister can reach Chromium for unindexed scopes even at capacity. Both subscription methods validate subscription URLs against the registration scope. Exceeding a limit rejects with TypeError before the native call; startup discards restored hints beyond the limits and logs how many.

Each wake-index write has a five-second caller deadline, including time in the queue. Physical writes are serialized. A subscribe that misses its deadline receives no native grant, and a late write is reconciled with current subscriptions. A committed native unsubscribe or unregister immediately updates in-memory eligibility. If persistence fails, retain the native result, retry the latest index and flush outstanding changes on clean quit. Unregistering a scope with no wake hints requires no write. While a write that missed its deadline is still in progress, new subscribes fail fast instead of queueing behind it; if the storage never settles that write, subscribes keep failing for the rest of the launch.

Closing a window releases its change registrations. Main also prunes destroyed or detached frames whenever a document registers or a visible change is delivered.

Wake-index reads retry EPERM, EBUSY and EACCES after 10, 20, 30 and 40 ms. If the index exists but remains unreadable, main warns once, starts with no restored hints and leaves the file untouched for that launch; hints written during the launch only drive in-memory delivery. The next launch reads the file again.

Dispatch cookiechange events in order per scope. Each ExtendableCookieChangeEvent owns a startTask() keepalive. A fulfillment or rejection reaction on a pending waitUntil promise can append another extension. Later events can start while earlier waitUntil promises are pending. Release the task on acknowledgement after dispatch and all extensions settle, send failure, worker destruction, five-minute timeout or quit. A finished event rejects further waitUntil calls with InvalidStateError.

### Known differences

The differential E2E baseline is Electron 45.0.0 / Chromium 156.0.8078.48. Rerun the native comparisons and review each boundary on Electron upgrades.

- The jar handles the cookie portion of Clear-Site-Data. Other data types, including cache and storage requested by `"*"`, have no jar-side clearing implementation. In the wildcard navigation comparison, HTTP localhost and HTTPS clear localStorage while the application scheme retains it.
- Partitioned cookies require Secure but share identity, deletion, quotas and eviction with ordinary cookies. A later write replaces the same name/domain/path, deletion with either partition setting removes it, and Cookie Store reports partitioned=false. Chromium's separate per-partition, per-domain 10,240-byte limit does not apply.
- A same-origin manifest link without crossorigin and a module worker created with credentials: "omit" load without cookies natively. On app:// they reach the handler without the omit marker, so the jar sends matching cookies and stores the response's Set-Cookie.
- Cache.add() and Cache.put() reject app:// request URLs with TypeError (Chromium's Cache API accepts only HTTP(S) requests), so app responses cannot be stored in CacheStorage.
- Same-origin no-cors fetch drops the omit marker. Dedicated and shared workers have no fetch wrapper. Their unmarked omit requests can send cookies and store the response's Set-Cookie. Opaque frames get no jar cookies even with include and SameSite=None. Other custom schemes do not participate.
- A same-origin omit fetch redirected to another origin carries the omit marker on the redirected request. The destination receives a CORS preflight for it, and the fetch rejects with TypeError unless the destination allows that header. A native fetch follows the redirect without a preflight.
- Explicit script Domain equal to APP_HOST creates a domain cookie, including on the single-label app host. Chromium normally treats Domain equal to a single-label host as host-only. Cookie Store reports the public host for a domain cookie and null for host-only.
- Initial and navigated about:blank subframes lack preload. They do not inherit the parent's jar cookies and same-origin omit fetches can carry cookies. A first change listener attached to another window's cookieStore through an about:blank frame's native addEventListener receives jar events only after that window registers through a wrapped listener path.
- A change between subscribe() and its resolution can reach the worker. Removing a registration outside wrapped unregister(), including clearing site data, can leave queued events eligible for a new registration at that scope. If a granted unregister() holder is destroyed or its lease expires before confirmation, main cancels queued events and keeps wake-only hints; if the native registration survived, delivery resumes after the next successful subscribe(). Main orders changes by when Electron reports them, so a store change made before subscribe() but reported after it can reach the worker.
- Window change and worker cookiechange events are synthetic and have isTrusted=false. The cookieStore object, its prototype and the event classes are native.
- Cookie Store errors keep Chromium's name, message and realm. Argument-validation failures, including from a CookieStore method borrowed by another same-origin window, reject in the window that supplied the method. Once a call reaches storage, its promise and storage errors (for example a refused HttpOnly overwrite) belong to the receiving store's window. Their stacks point into the shim. Invalid fetch input rejects with the native error type, but its message can name the Request constructor.
- A server Set-Cookie field containing invalid UTF-8 is ignored in full. Native Chromium can retain the original bytes. A document.cookie assignment whose name or value contains an unpaired UTF-16 surrogate is ignored; Chromium can store the resulting bytes and then return an empty document.cookie. cookieStore.set() replaces unpaired surrogates with U+FFFD in both.
- Clock-skew correction parses the response Date as an HTTP date (IMF-fixdate, RFC 850, asctime) or a named-month UTC date. Chromium also accepts legacy numeric forms such as 01/01/2000 00:00:00 GMT; for those the jar evaluates Expires against local time.
- If the desktop wake index is damaged, startup keeps the valid records and copies the original bytes to cookie-wake-index.json.corrupt. Unreadable hints are lost, so their workers can miss wakeups until the page subscribes again. New subscriptions keep working.
- The jar processes the first 50 Set-Cookie fields of a response and ignores the rest. Chromium has no per-response limit.
- An HttpOnly downgrade deletes and recreates the cookie. A same-value downgrade moves it after equal-path cookies created later; Chromium keeps the original creation time. Within one response, a later equal-path field can also precede the recreated cookie in Cookie headers and document.cookie, even when the value changes.
- During store failure, document.cookie returns the latest successful snapshot for the cookie URL, or the empty string if that URL has no successful read or its snapshot was evicted from the 100-entry cache. Pending notifications and unfinished or failed refreshes can leave it stale. A change, including an HttpOnly transition, refreshes only snapshots whose pathname matches the changed cookie's Path. Background refreshes share one outstanding native read per pathname, including across timeouts. Each full cookie URL takes the result only if its snapshot is still current.
- Concurrent responses changing several of the same cookie identities can interleave when an HttpOnly downgrade requires a retry. The final state can differ from either whole-response order.
- Cookies saved by older versions that forced HttpOnly keep their stored flags. There is no migration.

## Session permissions (HOST-10)

Install permission request, permission check and device handlers immediately after creating the application session, before loading any page. Permissions default to denied. Only a live application main frame may request clipboard-sanitized-write or fullscreen; unknown origins, sub-frames and requests without a verifiable document are denied. Permission checks also validate the requesting origin. The adapters preserve the different Electron API shapes rather than inferring a sub-frame's identity from the top-level URL.

An openExternal permission additionally requires an explicit http, https or mailto target, using the same URL predicate as main-process external navigation. Main-process shell.openExternal calls retain their own validation. Device access (including HID, serial and USB), notifications, media and other permissions are denied. Log only the rejected permission name, never the requesting URL or device details.

Derived applications can extend this policy deliberately, keeping request/check decisions consistent and adding permission-specific verification. Allowing media in this policy does not bypass operating-system consent; macOS camera and microphone access also needs the matching Info.plist usage descriptions.

## Build profiles (HOST-11)

A build profile is fixed when the desktop bundles are built (`DESKTOP_BUILD_PROFILE`, compiled in) and never chosen at run time. Compiling profiles in avoids shipping test, development or diagnostic capabilities in release where a missed runtime check could expose them, and lets `test` keep the Node inspector needed by Playwright while `release` disables it. `dev` is built only by `dev:desktop`, in watch mode. Playwright, smoke and benchmarks use explicitly built `test` bundles. Desktop builds default to `release`, the only profile that ships. Each profile has its own bundle directory, and the test and release packages have separate output directories. Test launchers and the release verifier check the running profile through the first log line or, under Playwright, `globalThis.desktopBuildProfile`.

What a profile contains is decided by the build configuration, not by tree-shaking or runtime checks: `PROFILE_ENTRIES` in `scripts/build-profile.ts` aliases each listed module to an empty implementation of the same contract in the profiles that exclude it.

The remote debugging refusal is the first statement of the release main entry; it checks Chromium's command line and argv in every spelling Chromium accepts. Other Chromium switches are not restricted.

Environment variables belong to profiles. LOG_LEVEL, DESKTOP_CHROME_MODE and the system's XDG_CURRENT_DESKTOP/XDG_SESSION_TYPE are read by every profile. DESKTOP_SMOKE, DESKTOP_SMOKE_LAYOUT, DESKTOP_SMOKE_SCREENSHOT, DESKTOP_BENCH, DESKTOP_BENCH_CASES, DESKTOP_BENCH_WARMUP_MS, DESKTOP_BENCH_MEASURE_MS, DESKTOP_BENCH_LABEL, DESKTOP_E2E, DESKTOP_BOOT_PROFILE and DESKTOP_PORT_ACK_COALESCE (`DEBUG_ENV` in `src/debug-env.names.ts`) are read by dev and test builds only. DESKTOP_USER_DATA_SUFFIX is read by the dev build only; test launches choose their directory with `--user-data-dir`. DESKTOP_BUILD_PROFILE (set by `build.ts` and `dev.ts`, read by `vite.base.config.ts` and compiled in), DESKTOP_DEV_PORT (`dev.ts` and the web dev server it starts) and BENCH_VERBOSE (`bench.ts`) are read by scripts and build configuration, never by the app at run time.

Test and release JavaScript are different artifacts built from the same source, so a test result does not transfer to release automatically. A result obtained on test applies to release only where this table says the two agree; the table is the contract that `verify:build` and `verify:release` guard. Adding a debug capability means adding it to `PROFILE_ENTRIES` and to the `verify:build` markers; a release-only failure outside the difference table is observable only through `verify:release` or manual checks.

## Verification requirements

Check real SSR/SPA pages, API, CSP, navigation, redirects, streaming/backpressure/cancellation, bounded lifecycle/recovery, rejected navigation/IPC/header spoofing, preferences and cookie persistence, development reload/restart and packaged resources. Each layer establishes only what it observes.

Unit tests (Vitest) cover pure logic, including each profile's Vite configuration, the fuse table and the `verify:release` verdicts. They launch no application; some spawn Node or run Vite builds.

`verify:build` needs an existing web build and, unless `--no-build` checks the bundles on disk, runs through pnpm to build the test and release bundles. It checks the bundler's module records and the bundle text: release contains nothing of `src/diagnostics` but its empty entry, no development host, no debug-environment module, no debug or development variable name, no diagnostic route prefix or result marker, no `desktopBuildProfile`, no `DESKTOP_*` name but DESKTOP_CHROME_MODE, and main.cjs carries the remote debugging refusal. The test bundles are the positive control: the same detectors must find every marker that belongs to them. It proves bundle contents, not runtime behavior; dev bundles are not checked.

Playwright (`test:e2e`) drives the test profile only, unpackaged and packaged; the packaged project starts after a setup project reads the package's fuses back. It covers host behavior, including IndexedDB writes and deletions after transaction completion and persistent cookies across reload, window reopen, full restart and hard kill. Host E2E must not depend on demo text or controls; explicitly tagged demo suites retain layout and appearance interaction coverage. `test:e2e` runs both suites for template acceptance; derived applications can retain only `test:e2e:host`. Playwright attaches a debugger to every renderer, and an unresponsive renderer has never been reported under E2E (measured); hangs are observable only in launches without it (smoke, benchmark, `verify:release`). E2E refuses to start on a locked macOS screen, where window visibility, focus and full screen cannot be observed. On Linux Playwright adds `--no-sandbox` unless `chromiumSandbox` is set; E2E sets it wherever the sandbox can start.

The smoke (DESKTOP_SMOKE through `pnpm --dir apps/desktop start:test`, unpackaged or `--packaged`) runs machine-readable self-checks inside a test build; DESKTOP_SMOKE_LAYOUT explicitly adds the template demo matrix. Its SSE check covers transport rather than an application SSE feature. The benchmark measures the test build, unpackaged or packaged, and records the target and fuse readings with each run.

Test launches (Playwright, smoke, benchmark, `start:test`) share `scripts/launch.ts`. `launchSpec()` builds the command, arguments and environment: it requires a user data directory and adds `--user-data-dir`, `--use-mock-keychain` and `-ApplePersistenceIgnoreState YES` on macOS (the latter keeps a launch after a startup crash past AppKit's modal reopen-windows prompt; `verify:release` passes it too), `--password-store=basic` on Linux and, on Linux where Chromium's sandbox cannot start (running as root, user namespaces unavailable or restricted by AppArmor, which on Ubuntu applies to every unpacked build, and no root-owned 4755 `chrome-sandbox`), `--no-sandbox` with a notice. The callers take a fresh directory from `freshUserDataDir()` (one per E2E test, benchmark run or `start:test` invocation), call `checkLaunchInputs()` for the fuse read-back of a packaged launch or the web build check of an unpackaged one, and check the reported profile with `verifyBuildProfile()` or, under Playwright, the fixture's `desktopBuildProfile` evaluation.

Users launch the packaged release application directly or with `pnpm start:desktop`. Automated release verification runs through `verify:release` and never uses Playwright. It builds the web app, both profiles' bundles and both packages unless `--no-build` is given, then runs five checks, each reported as pass, fail or skipped with a reason: (1) the six fuses read back match the release column; (2) the final app.asar holds exactly the release manifest and bundles with matching integrity (on macOS also the Info.plist header hash), the bundles are byte for byte those `verify:build` checks, and every client resource matches the Web build digest embedded in the shipped utility; (3) `--remote-debugging-port` and `--remote-debugging-pipe` each end in exit status 97 and the refusal line with nothing listening or answering, while the test package started the same way must answer, as positive control; (4) on a fresh `--user-data-dir`, the main process reports release, logs `main window loaded and shown` within 30 seconds, exits 0 on SIGTERM (`taskkill` without `/F` on Windows) with every process it created gone, writes into that directory and leaves the installed application's userData unchanged; on Windows it must log `cookie key stored before start` and `cookie key checked: this launch uses the stored key` exactly once each, with no mismatch, no writer warning and no failure record, and elsewhere none of these lines; a failure carries the main process's last log lines with their times, the kinds of process still running and the end of stderr; on a locked macOS screen the check is skipped; (5) signing and notarization are skipped for a local unsigned package and required on macOS and Windows with `--distribution`. It exits 0 when verified, 1 when a check failed, and 2 when incomplete: nothing failed but one of checks 1–4 (or 5 for a distribution package on macOS or Windows) was skipped, including check 4 on a locked macOS screen. The Windows cookie key assertions of check 4 passed on Windows 11 arm64 (measured); their failure cases have unit tests only. The first launch of a freshly written package is slower on macOS (measured 1.8–2.0 s to ready against 0.5 s), well within the deadline. On Linux hosts where the sandbox cannot start, checks 3 and 4 are skipped unless `--allow-no-sandbox` runs them with `--no-sandbox`, which their result lines state. It proves the shipped package's fuses, contents, debugging refusal and clean startup and quit, not application behavior, which only the test profile exercises.

If the port accepts a connection only on the probe after exit, and the refusal otherwise passes including process cleanup, check 3 repeats the release launch once on a newly allocated port. A listener detected during the launch fails the check directly.

The main bundle compiles the matching Web render mode into `DESKTOP_SSR`. Test and release builds read the resolved mode emitted by the Router build, and dev uses the live Router config. `verify:build` checks the first-window cookie pre-write marker against that Web build in both profiles.

Test launches and check 4 use `--use-mock-keychain` on macOS (verified on the release package) and `--password-store=basic` on Linux. On Windows they use the current user's DPAPI; when the cookie key writer runs, it encrypts a probe with safeStorage and the launching app verifies it by decrypting it. A released application uses the real credential store (measured on unsigned release packages). Before creating the first window, main reads cookies at the private HTTPS origin immediately and every two seconds until a read settles or three minutes elapse, so answering a keychain or keyring prompt within that time allows navigation to start with a responsive store. If the read fails or times out, main logs a warning and opens the window with the usual five-second request deadline. On macOS the first launch creates the `<productName> Safe Storage` item without a prompt. A launch whose code signature differs from the one the item trusts, such as an ad-hoc-signed upgrade, asks for the login password. Always Allow keeps the existing key and later launches do not ask. Deny keeps the item and key unchanged and the app still starts, but every later launch asks again, and Chromium deletes every persistent cookie it cannot decrypt: they are gone even after a later Always Allow, and cookies written while access is denied stay in memory only (measured on the packaged test app with cookie encryption and the real keychain). Signed builds avoid the upgrade prompt, and with it this loss, only while the signing identity stays the same. On Linux with an unlocked Secret Service the first launch creates the item and an upgrade reuses it; without a Secret Service the app starts and quits normally, and the fallback key choice was not observed because the release app writes no cookie. Installer and distribution checks belong to the actual release configuration.
