# Electron host specification

## Process boundaries (HOST-01)

The desktop host reuses the web client, Hono host and API. Production opens no TCP listener for pages or API. Main owns windows, the dedicated session, protocol mapping, utility lifecycle and restricted system bridges. Sandboxed preload is a single CommonJS file. The utility process runs `createWebApp`, SSR or SPA hosting, static files, API and port-fetch as ESM under Node resolution conditions. The renderer uses the same web client build without Node integration.

Build outputs are `main.cjs`, `preload.cjs` and `utility.mjs`. Main must not import `@repo/server` or top-level await `app.whenReady()`. Shared contracts are browser-safe. Transport packages remain independent of Electron and testable under Node. Electron is pinned in package metadata; upgrades require validation rather than a runtime version allowlist.

## Protocol mapping (HOST-02)

Requests follow `app://app` → dedicated-session protocol handler → internal HTTP URL → MessagePort/port-fetch → utility `createWebApp().fetch(Request)` → streamed response. Register standard, secure, supportFetchAPI, stream, corsEnabled and codeCache privileges before ready. Reject targets outside `app://app`. `main/app-url.ts` defines the stable scheme/host/origin and shared URL check; keep that origin independent of product names and APP_ID. Changing it requires a browser-storage migration.

The internal origin provides server URL/same-origin semantics, not a listening port. Map URL, relevant Origin/Referer and response Location. Non-GET/HEAD requests receive a trusted internal Origin and Sec-Fetch-Site for Hono CSRF and Router checks. Strip renderer-supplied Cookie and X-Desktop-* before injecting actual host state and preferences. Web hosts remove desktop headers; headers cannot establish desktop identity.

Server redirects use relative paths, including Router `.data` redirects embedded in response bodies. Do not derive public absolute links from internal request URLs. Static files and SPA HTML belong only to the web host. The development proxy uses manual redirects to preserve status and Location.

## Transport and utility lifecycle (HOST-03)

Port-fetch multiplexes request IDs with Request/Response headers, status and bidirectional bodies. Return response streams as soon as headers arrive. Acknowledgement windows bound unconsumed bytes and pause upstream reads. Chunks use standalone Uint8Array buffers so cloning a subarray does not copy a larger backing store. No zero-copy guarantee applies; Electron ports receive no ArrayBuffer transfer list.

Cancellation, timeout, port closure, early response and stream error clean up both ends idempotently. Closed ports reject new requests. Before response handoff, main correlates the application session's webRequest disconnect with its protocol request by network ID, including during cookie lookup. The protocol handler owns the application session’s `onBeforeSendHeaders`, `onErrorOccurred` and `onCompleted` listeners. Registering another listener for the same event replaces the existing one. Main removes the internal correlation header before forwarding. After handoff, cancelling the response body also cancels the upstream request. Utility handlers propagate their request signal to downstream work. Both desktop modes bound the upstream header wait to 60 seconds while SSE and download bodies may continue. The development proxy retries only GET and HEAD on transient connection failures.

Adapt MessagePortMain event shapes and start semantics, transferring ports only after utility spawn. Utility state is explicitly idle/starting/running/stopping/stopped. Concurrent starts share readiness. Fork-to-ready times out after 20 seconds; shutdown has a 3-second grace period. Shutdown forbids automatic restart. A utility retired or stopped before it spawned is killed as soon as it exists. Increasing generations coordinate restart/readiness with window recovery.

## Identity, trust and CSP (HOST-04)

Host identity comes from `createWebApp({ shell })`; development uses WEB_SHELL configuration. Stable shell facts and trusted per-request window/preferences data are distinct. SSR supplies root seeds; SPA reconnects through preload according to the layout lifecycle.

The renderer uses contextIsolation, sandbox and no nodeIntegration. Explicitly disable nodeIntegrationInSubFrames and webviewTag; preload exposes its bridge, registers teardown and signals first paint only when process.isMainFrame. The application has a dedicated persistent session. Navigation and redirects stay on app://app. Main-frame external http/https/mailto links go to the system browser; external sub-frame navigation and redirects are blocked without opening another application. Same-origin sub-frame navigation remains allowed. New-window requests for app://app open independent application windows with the same session, preload and shared utility. Each window owns its chrome IPC and recovery state. Dock activation and second-instance launches can reopen the primary window while independent windows retain their state. Same-origin windows that retain an opener can share a Chromium renderer and recover together after its exit. A healthy document survives replacement of the shared utility. Child windows use the current native theme at creation. IPC verifies the registered BrowserWindow, its current webContents, current main frame, and frame protocol/host; comparing opaque origin alone is insufficient.

The desktop demo assigns the settings route a window key. Reopening settings from any window restores and focuses its existing window without reloading the document. Closing that window or navigating it away releases the key. Other new-window requests keep their normal popup and opener semantics. Automatically placed siblings cascade within the opener's display work area where the window manager permits positioning. Explicit popup coordinates and dimensions take precedence.

Capture main exceptions in logs instead of blocking default dialogs. Once stdout fails, the main logger drops later lines instead of reporting the failure to the same stream. Protocol/port failures are explicit. Logs omit credentials, full bootstrap/preferences and sensitive queries. `main/log-url.ts` bounds URL fields and removes credentials, query and fragment; opaque URLs expose only their scheme. Error messages/stacks and forwarded main-frame console text redact recognized absolute URLs while retaining diagnostics. Paths, free text and other structured fields still require caller-level care; the main logger does not sanitize forwarded utility output. Single-instance locking, utility shutdown and listener cleanup are required. A window whose renderer exits while the window is closing is destroyed rather than reloaded, so quitting cannot stall on it; a page that vetoes unload keeps its window and recovery. Windows log `window unresponsive` (warn) and `window responsive again` (info). macOS activation can create/register a new window after closure. Desktop identity is not business authorization and never grants arbitrary proxy destinations.

The web host owns CSP. SSR uses one document nonce across React, ServerRouter, Links, ScrollRestoration and Scripts; revalidation cannot replace the active document nonce. Static SPA/prerendered HTML uses hashes, identical for GET/HEAD, and does not serve document ranges. Production script-src excludes unsafe-inline. Inline chrome safety styles require the configured style policy independently of script policy.

## Development and startup (HOST-05)

`pnpm dev:desktop` starts a separate desktop-mode Router dev server and Electron. Pages remain app://; main proxies to development HTTP without running utility. Mapping/trust rules remain the same. Development watches builds, restarts Electron after main/utility changes, reloads after preload changes and waits for the old process to exit. The default port is 5174, configurable with DESKTOP_DEV_PORT; HMR host/clientPort are explicit. Development runs the dev build profile (HOST-11) on `<userData>-dev`; DESKTOP_USER_DATA_SUFFIX, read only by the dev build, changes the suffix. Electron is started without `windowsHide`, which on Windows hides its first window (measured on Windows 11); console children keep it.

After registering the protocol, ready prepares the hidden window and utility concurrently. Document requests await utility readiness. A trusted preload notification after two animation frames shows the window; ready-to-show has a one-second fallback. Bootstrap enhancement does not gate display. Every launch that starts the application logs `{"buildProfile":…,"msg":"build profile"}` at info as its first main-process line; a release launch refused for remote debugging logs only the refusal, and the Windows cookie key writer copy (HOST-09) logs nothing. It then logs `main window loaded and shown` at info once per process, when the primary window holds a finished document answered with a 2xx status and is shown; HTTP error documents, Chromium error pages and hidden windows never produce it. A window counts as shown on its `show` event or, right after the application itself showed it, when it reports itself visible: on macOS `show` follows occlusion and does not arrive while the screen is locked (measured). That second path has unit tests only; it has not been exercised in a real locked session. LOG_LEVEL cannot suppress either line; external launchers depend on both. Utility NODE_COMPILE_CACHE resides in userData. Startup evaluation compares repeated same-environment medians and stage timings, not a universal cold-start promise.

## Build and packaging (HOST-06)

Build web first, then the three desktop entries of one build profile (HOST-11), then electron-builder with that profile's leaf configuration (`electron-builder.test.yml` or `electron-builder.release.yml`, both extending `electron-builder.base.yml`). Root package:desktop/release:desktop/dist:desktop include builds; package-local packaging scripts consume existing builds. Packaging and every unpackaged test launch (`checkLaunchInputs()` in `scripts/launch.ts`; dev launches are not checked) first check that the profile's utility bundle and `apps/web/build/client` come from the same web build: every hashed client asset the utility references must exist, and the server entry must still have the SHA-256 recorded in `.vite/<profile>/web-server.json` when the utility was built. ASAR contains the profile's entry bundles and package metadata, without source maps, module records or the web server record. Client resources are copied to resources/client and served by utility. Bundled web/server dependencies are not duplicated as runtime node_modules. Only required external native modules belong in dependencies; native modules require Electron ABI and rebuild-policy verification.

Root build, build:desktop, release:desktop and dist:desktop run their child builds with NODE_ENV=production and without inherited development server variables. Test and release bundles are minified, replace process.env.NODE_ENV with production and never embed a development server URL; only the dev profile, built in watch mode by `dev:desktop`, does. The utility always hosts a built application and receives NODE_ENV=production, regardless of its parent's environment. Building only the desktop entries (`pnpm --filter desktop build [test | release]`) consumes the existing web build, so use build:desktop or release:desktop before packaging.

`apps/desktop/package.json` supplies `productName`, checked against `electron-builder.base.yml`. It determines the default Electron app name and hence userData; builder `appId` is separate. Choose these values together with shared `APP_ID` for each derived project. Preference files, visual mirror and compile cache retain their filenames within userData.

Packaged E2E derives macOS bundle/executable and Windows executable names from productName. Linux follows electron-builder's default lowercased package name, not productName. The launchers look in `out/test` (`verify:release` in `out/release`), support the existing platform/architecture output directories and no executableName override. Name validation accepts a leading ASCII letter and subsequent ASCII letters, digits, spaces, dots, underscores or hyphens, rejects trailing dots/spaces and Windows reserved filenames, and keeps builder sanitization from changing the expected path.

Both packages take their fuses from one table (`FUSES` in `scripts/fuses.ts`), flipped by each leaf configuration's afterPack hook: RunAsNode, NodeOptionsEnvironmentVariable and NodeCliInspectArguments off; CookieEncryption, EmbeddedAsarIntegrityValidation and OnlyLoadAppFromAsar on. The test package differs only in keeping NodeCliInspectArguments on, which Playwright's Electron driver needs. Every packaged test launch first reads the six fuses back from the final binary (`checkLaunchInputs()`) and refuses a package that does not match the test column; `verify:release` reports the release read-back as its check 1 and runs its other checks regardless. Unpackaged runs use the checkout's Electron, whose fuses are never flipped, so they have no cookie encryption and no asar checks.

Installers (macOS dmg/zip, Windows NSIS, Linux deb/rpm; rpm requires rpmbuild) are built only from the release profile (`dist:desktop`, into `out/release`); `out/test` holds only the unpacked test app. No signing identity is configured. Signing, notarization, distribution channels and automatic updates are not supplied as completed release services. Linux installation must satisfy sandbox permissions; --no-sandbox is not a default release solution.

## Bidirectional channels (HOST-07)

`@repo/channel` provides MessagePort/WebSocket adapters and relay with ordered delivery, backpressure and bounded connection/queue handling. Producers await whenDrained; send itself does not block or drop frames. Channel is distinct from request/response port-fetch. The template does not expose an application gateway connection, renderer sandbox connection or BFF streaming route merely because the transport package exists.

## Preferences (HOST-08)

Page scripts under app://app cannot read or write cookies. Small client-written, server-read display preferences use a common helper with host-specific storage. Web names cookies by concatenating `PREFERENCE_COOKIE_PREFIX` and the key. The prefix is `cookieName("pref_")` from `@repo/shared` (default `framework-app_pref_`). Cookies contain JSON values, percent-encoding characters disallowed in cookie values, Path=/, SameSite=Lax, one-year Max-Age and Secure on HTTPS. Duplicate names use the first, most specific path match. Desktop uses main-process memory and userData/prefs.json, atomically replaced after temporary-file fsync; transient Windows rename failures retry within about 100ms. Values take effect only after successful persistence.

The web helper is `~/platform/electron/preferences`, with host contexts in `~/platform/electron/shell`. Old `pref-*` cookie names are not read; resetting those template preferences is intentional and no compatibility layer is added. Visual preference localStorage and visual cookie names keep their existing derived values.

Desktop injects x-desktop-prefs on every request. Preload setPref/removePref invokes validated main IPC. Loader/action `getPreference(context, key)` returns undefined for absent/invalid values. Host context chooses the source: web cookies or desktop request preferences, never an untrusted request-selected mode. `useSetPreference()` writes and revalidates; null deletes; failures reject with PreferenceError/reason. `writePreference(shell, key, value)` works outside React without automatic revalidation. After a changed value is persisted, other open desktop documents coalesce notifications and revalidate their active loaders, including a final refresh for changes made during an in-flight refresh. A new subscription checks its rendered snapshot against the main store to cover writes during hydration. Business code uses these helpers rather than shell branches or direct cookie writes.

There is no general client-side read API for SPA/clientLoader. Supply loader data or design an explicit read bridge when needed. Keys start with a letter and contain letters/digits/underscore/dot/hyphen, at most 64 characters. Values are strings of at most 1024 UTF-16 units, finite numbers or booleans. Both hosts enforce both 4096-byte aggregate limits: ASCII JSON with non-ASCII escaped, and the encoded preference cookie header using that same prefix including separators. Oversized updates reject before writing; deletion is always accepted.

Preferences are user-controlled display settings, never credentials, sessions, authorization inputs or bulk data. High-frequency changes persist on commit rather than every frame. Main is the final validator. Invalid requests return rejected without changes; disk failure returns persist-failed with the previous value intact. Malformed files become empty and invalid entries are discarded. Logs omit preference values. Browser desktop-header spoofing is stripped before trusted injection.

## Server cookies (HOST-09)

Main owns server Set-Cookie/Cookie round trips for both utility and development proxy paths because app:// and protocol-handler responses do not receive native network cookie handling. Server/web code retains ordinary cookie semantics. The dedicated session stores host-only cookies using `https://app.desktop`, matching the internal host but permitting Secure storage. The CookieEncryption fuse of both packages encrypts persisted values; unpackaged runs store them unencrypted.

Parse all Set-Cookie fields in order, complete writes/deletions and flushStore before returning the response; remove Set-Cookie before renderer delivery. Replace any renderer Cookie header with stored cookies matching the request path, longest Path first. Read failure logs a warning and continues without cookies. Pure parsing/serialization lives in cookie-jar.ts; Electron adapters own storage.

| Rule          | Desktop behavior                                                                                                                                                                                                                        |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Domain        | Accept only the internal host (also the dev server host during development), ignoring case/leading dot; store host-only; reject other domains                                                                                           |
| Path          | Use an absolute supplied path or the request default directory; enforce browser path matching                                                                                                                                           |
| Expiration    | Max-Age takes precedence over Expires; cap lifetime at 400 days; nonpositive Max-Age/past Expires deletes; invalid expiration leaves a session cookie                                                                                   |
| Secure        | Use HTTPS storage to support Secure cookies                                                                                                                                                                                             |
| HttpOnly      | Parse the flag for prefix validation; store all cookies as HttpOnly so a later replacement can overwrite an existing HttpOnly cookie; page scripts cannot access any cookie                                                             |
| SameSite      | Store the attribute but do not filter sending by it; all application requests attach matching cookies. Reject None without Secure. If third-party frames are explicitly permitted, rely on Origin/CSRF checks for cross-site navigation |
| Prefixes      | Case-insensitive: __Secure- requires Secure; __Host- additionally forbids Domain and requires explicit Path=/; __Http- requires Secure and HttpOnly; __Host-Http- combines both rules                                                   |
| Limits        | Name plus value at most 4096 bytes; ignore attributes over 1024 bytes; process at most 50 cookies per response                                                                                                                          |
| Invalid input | Ignore control characters and nameless cookies; log bounded rejection metadata without values                                                                                                                                           |

Any mutation flushes before response delivery, including replacing persistent cookies with session cookies so stale disk values cannot reappear. After all windows accept quit, flush with a two-second bound in parallel with utility shutdown. A window that cancels quit retains its working host and recovery. Session cookies survive reload/window reopening but not process restart. Persistent cookies survive restart, and a crash or kill after the response that set them. On Linux a signal to the application's whole process group (a session logout, or a direct launch interrupted from its terminal) can make Chromium abort instead of quitting (measured: the GPU process dies first); nothing already flushed is lost. `pnpm --filter desktop start` keeps the application in its own process group and passes signals to the main process only.

On Windows the encryption key's only copy on disk is in `<userData>/Local State`, which Chromium writes about 10 seconds after a new profile starts or at a clean quit (measured on Electron 45, Windows 11 arm64; [electron/electron#55978](https://github.com/electron/electron/issues/55978), open). A test or release launch whose Local State has no key therefore, once it holds the single-instance lock, runs a copy of the app with `--desktop-cookie-key-writer` on the same userData and waits for it (at most 5 seconds): the copy lets Chromium create the key, prints a probe encrypted with the synchronous safeStorage API and quits at ready, which makes Chromium write Local State and its own directories (such as Crashpad and caches); the copy writes nothing of the application's. The launch reads Local State only after its main script's synchronous part, so it starts on that key (measured, not documented by Electron); it logs `cookie key stored before start`, then, once its first window is on its way, whether it decrypts the probe (`cookie key checked: this launch uses the stored key`, or an error). The probe relies on safeStorage sharing the cookie encryption key, measured for the synchronous API only; Electron 45 marks that API deprecated, and if it disappears the launch logs that it cannot check the key, which stays stored. The writer's wall time is noted in the boot profile as `cookie-key-writer-ms`; every launcher run on Windows includes it, as each uses a fresh profile.

Only a Local State that is absent or parses without a key counts as missing. After a run that leaves the key missing, `cookie-key-writer-failed.json` in userData records the time and application version; for a day, launches of that version skip the writer with a warning, and a launch that finds the key deletes the record. A Local State that stays unreadable or unparseable after a few short retries is reported as unknown and records nothing. A packaged profile without a stored key can lose persistent cookies set in a first launch that dies within about 10 seconds; unpackaged launches do not encrypt cookies and lose nothing. An uncaught error in the writer ends it with a non-zero status instead of Electron's blocking dialog. Dev builds never run the writer. The writer is refused like any release launch with a remote debugging switch and receives only `--user-data-dir`, `--disable-gpu`, its own switch and, unpackaged, the application directory. The mechanism was measured on Windows 11 arm64 only; Windows x64 is not verified, and the handling of unreadable Local State, the failure record's expiry and version, and the crash exit have unit tests only.

Cookies attach only to app:// handler upstream requests, never arbitrary targets. Code must not request the storage origin in the application session. The .desktop suffix is not a reserved TLD; future delegation would create a risk if such network requests were allowed. The renderer remains restricted to app://app and CSP does not allow that storage origin. Logs omit Cookie/Set-Cookie contents.

E2E routes mount only with DESKTOP_E2E=1 in dev and test builds; release builds contain neither the routes nor the variable name (HOST-11). Page document.cookie stays empty. All app requests are same-origin and attach cookies regardless of fetch credentials mode. Nameless cookies are unsupported. Development uses `<userData>-dev` and every test launch a fresh `--user-data-dir`, so neither shares cookies with the installed application.

## Session permissions (HOST-10)

Install permission request, permission check and device handlers immediately after creating the application session, before loading any page. Permissions default to denied. Only a live application main frame may request clipboard-sanitized-write or fullscreen; unknown origins, sub-frames and requests without a verifiable document are denied. Permission checks also validate the requesting origin. The adapters preserve the different Electron API shapes rather than inferring a sub-frame's identity from the top-level URL.

An openExternal permission additionally requires an explicit http, https or mailto target, using the same URL predicate as main-process external navigation. Main-process shell.openExternal calls retain their own validation. Device access (including HID, serial and USB), notifications, media and other permissions are denied. Log only the rejected permission name, never the requesting URL or device details.

Derived applications can extend this policy deliberately, keeping request/check decisions consistent and adding permission-specific verification. Allowing media in this policy does not bypass operating-system consent; macOS camera and microphone access also needs the matching Info.plist usage descriptions.

## Build profiles (HOST-11)

A build profile is fixed when the desktop bundles are built (`DESKTOP_BUILD_PROFILE`, compiled in) and never chosen at run time. `dev` is built only by `dev:desktop`, in watch mode. `test` is the default of `pnpm --filter desktop build` and is what Playwright, the smoke and the benchmark run. `release` is the only profile that ships. Each profile has its own bundle directory and package directory, so no launcher or package can pick up another profile's bundles; launchers refuse a process that reports another profile (its first log line, or `globalThis.desktopBuildProfile` under Playwright).

What a profile contains is decided by the build configuration, not by tree-shaking or runtime checks: `PROFILE_ENTRIES` in `scripts/build-profile.ts` aliases each listed module to an empty implementation of the same contract in the profiles that exclude it.

| Bundles; package                                                                 | `.vite/dev`; none             | `.vite/test`; `out/test`, unpacked only           | `.vite/release`; `out/release`, unpacked or installers                                     |
| Minified, `NODE_ENV=production`                                                  | no                            | yes                                               | yes                                                                                        |
| Development server proxy and preload reload (`~/main/dev-host.ts`)               | yes                           | no                                                | no                                                                                         |
| Smoke, benchmark and E2E endpoints (`~/diagnostics/entry.ts`)                    | yes; the benchmark is refused | yes                                               | no                                                                                         |
| Debug environment variables (`~/debug-env.ts`)                                   | read                          | read                                              | neither read nor named                                                                     |
| `globalThis.desktopBuildProfile`                                                 | set                           | set                                               | absent                                                                                     |

The remote debugging refusal is the first statement of the release main entry; it checks Chromium's command line and argv in every spelling Chromium accepts. Other Chromium switches are not restricted.

Environment variables belong to profiles. LOG_LEVEL, DESKTOP_CHROME_MODE and the system's XDG_CURRENT_DESKTOP/XDG_SESSION_TYPE are read by every profile. DESKTOP_SMOKE, DESKTOP_SMOKE_LAYOUT, DESKTOP_SMOKE_SCREENSHOT, DESKTOP_BENCH, DESKTOP_BENCH_CASES, DESKTOP_BENCH_WARMUP_MS, DESKTOP_BENCH_MEASURE_MS, DESKTOP_BENCH_LABEL, DESKTOP_E2E, DESKTOP_BOOT_PROFILE and DESKTOP_PORT_ACK_COALESCE (`DEBUG_ENV` in `src/debug-env.names.ts`) are read by dev and test builds only. DESKTOP_USER_DATA_SUFFIX is read by the dev build only; test launches choose their directory with `--user-data-dir`. DESKTOP_BUILD_PROFILE (set by `build.ts` and `dev.ts`, read by `vite.base.config.ts` and compiled in), DESKTOP_DEV_PORT (`dev.ts` and the web dev server it starts) and BENCH_VERBOSE (`bench.ts`) are read by scripts and build configuration, never by the app at run time.

Test and release JavaScript are different artifacts built from the same source. A result obtained on test applies to release only where this table says the two agree; the table is the contract that `verify:build` and `verify:release` guard ([ADR 0011](../adrs/0011-build-profiles.md)).

## Verification requirements

Check real SSR/SPA pages, API, CSP, navigation, redirects, streaming/backpressure/cancellation, bounded lifecycle/recovery, rejected navigation/IPC/header spoofing, preferences and cookie persistence, development reload/restart and packaged resources. Each layer establishes only what it observes.

Unit tests (Vitest) cover pure logic, including each profile's Vite configuration, the fuse table and the `verify:release` verdicts. They launch no application; some spawn Node or run Vite builds.

`verify:build` needs an existing web build and, unless `--no-build` checks the bundles on disk, runs through pnpm to build the test and release bundles. It checks the bundler's module records and the bundle text: release contains nothing of `src/diagnostics` but its empty entry, no development host, no debug-environment module, no debug or development variable name, no diagnostic route prefix or result marker, no `desktopBuildProfile`, no `DESKTOP_*` name but DESKTOP_CHROME_MODE, and main.cjs carries the remote debugging refusal. The test bundles are the positive control: the same detectors must find every marker that belongs to them. It proves bundle contents, not runtime behavior; dev bundles are not checked.

Playwright (`test:e2e`) drives the test profile only, unpackaged and packaged; the packaged project starts after a setup project reads the package's fuses back. It covers host behavior, including IndexedDB writes and deletions after transaction completion and persistent cookies across reload, window reopen, full restart and hard kill. Host E2E must not depend on demo text or controls; explicitly tagged demo suites retain layout and appearance interaction coverage. `test:e2e` runs both suites for template acceptance; derived applications can retain only `test:e2e:host`. Playwright attaches a debugger to every renderer, and an unresponsive renderer has never been reported under E2E (measured); hangs are observable only in launches without it (smoke, benchmark, `verify:release`). E2E refuses to start on a locked macOS screen, where window visibility, focus and full screen cannot be observed. On Linux Playwright adds `--no-sandbox` unless `chromiumSandbox` is set; E2E sets it wherever the sandbox can start.

The smoke (DESKTOP_SMOKE through `pnpm --filter desktop start`, unpackaged or `--packaged`) runs machine-readable self-checks inside a test build; DESKTOP_SMOKE_LAYOUT explicitly adds the template demo matrix. Its SSE check covers transport rather than an application SSE feature. The benchmark measures the test build, unpackaged or packaged, and records the target and fuse readings with each run.

Test launches (Playwright, smoke, benchmark, `start`) share `scripts/launch.ts`. `launchSpec()` builds the command, arguments and environment: it requires a user data directory and adds `--user-data-dir`, `--use-mock-keychain` on macOS, `--password-store=basic` on Linux and, on Linux where Chromium's sandbox cannot start (running as root, user namespaces unavailable or restricted by AppArmor, which on Ubuntu applies to every unpacked build, and no root-owned 4755 `chrome-sandbox`), `--no-sandbox` with a notice. The callers take a fresh directory from `freshUserDataDir()` (one per E2E test, benchmark run or `start` invocation), call `checkLaunchInputs()` for the fuse read-back of a packaged launch or the web build check of an unpackaged one, and check the reported profile with `verifyBuildProfile()` or, under Playwright, the fixture's `desktopBuildProfile` evaluation.

`verify:release` is the only launcher of a release package and never uses Playwright. It builds the web app, both profiles' bundles and both packages unless `--no-build` is given, then runs five checks, each reported as pass, fail or skipped with a reason: (1) the six fuses read back match the release column; (2) the final app.asar holds exactly the release manifest and bundles with matching integrity (on macOS also the Info.plist header hash), the bundles are byte for byte those `verify:build` checks, and the client assets the shipped utility references are in the resources; (3) `--remote-debugging-port` and `--remote-debugging-pipe` each end in exit status 97 and the refusal line with nothing listening or answering, while the test package started the same way must answer, as positive control; (4) on a fresh `--user-data-dir`, the main process reports release, logs `main window loaded and shown` within 30 seconds, exits 0 on SIGTERM (`taskkill` without `/F` on Windows) with every process it created gone, writes into that directory and leaves the installed application's userData unchanged; on Windows it must log `cookie key stored before start` and `cookie key checked: this launch uses the stored key` exactly once each, with no mismatch, no writer warning and no failure record, and elsewhere none of these lines; a failure carries the main process's last log lines with their times, the kinds of process still running and the end of stderr; on a locked macOS screen the check is skipped; (5) signing and notarization are skipped for a local unsigned package and required with `--distribution`. It exits 0 when verified, 1 when a check failed, and 2 when incomplete: nothing failed but one of checks 1–4 (or 5 for a distribution package on macOS or Windows) was skipped, including check 4 on a locked macOS screen. The Windows cookie key assertions of check 4 have unit tests only until a Windows run confirms them. The first launch of a freshly written package is slower on macOS (measured 1.8–2.0 s to ready against 0.5 s), well within the deadline. On Linux hosts where the sandbox cannot start, checks 3 and 4 are skipped unless `--allow-no-sandbox` runs them with `--no-sandbox`, which their result lines state. It proves the shipped package's fuses, contents, debugging refusal and clean startup and quit, not application behavior, which only the test profile exercises.

No automated layer exercises the real OS credential store: test launches and check 4 use `--use-mock-keychain` on macOS (measured on the release package: the login keychain is neither read nor given an item) and `--password-store=basic` on Linux, and Windows uses DPAPI for the current user. A released application may prompt for the macOS Safe Storage keychain item or depend on a Linux keyring; check that by hand. Installer and distribution checks belong to the actual release configuration.
